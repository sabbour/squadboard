# Cross-Surface Squad Sync Architecture Contract

**Status:** Foundation decision (McManus)  
**Date:** 2026-05-19  
**Surfaces:** Squadboard (web/API), CLI/Copilot agents, local filesystem, MCP broker

---

## Problem Statement

Users face three critical gaps when starting projects:

1. **Squadboard-first path:** Create a project in Squadboard. Later open Copilot/CLI without `.github/agents/squad.agent.md` → no Copilot Squad available.
2. **CLI-first path:** Start with Copilot/CLI, build `.squad/` on disk. Add Squadboard later → unclear if filesystem remains authoritative or Squadboard imports then owns state.
3. **Ceremonies empty:** Projects created in either surface have empty `.squad/ceremonies.md` → no defaults seeded, users must manually bootstrap workflows.

**Root cause:** No explicit contract defining source-of-truth authority, bootstrap ownership, or sync semantics. Current state is implicit partial mirroring — filesystem `.squad/` can drift from Squadboard DB, and client agent files live outside scope.

---

## Architectural Principles

1. **Mode-based authority, not continuous sync.** Each project locks to ONE source-of-truth mode at creation. We mirror *when asked*, not continuously.
2. **Explicit bootstrap/projection.** Bootstrap is a one-time import; projection is a repeatable generation/sync from the source of truth.
3. **Client surfaces are read-only projections of authoritative state.** `.github/agents/squad.agent.md` and ceremonies defaults are generated artifacts, not sources.
4. **Drift detection replaces silent data loss.** When surfaces diverge, report it; don't silently pick winners.
5. **The Squad SDK is a library, not an oracle.** It provides storage backends (filesystem or PostgreSQL). It does not dictate what owns state — the application layer does.

---

## API Namespace Decision

Use the project-scoped namespace **`/api/projects/:projectId/squad-sync/...`** for this workstream.

**Why:** Existing backend conventions expose project resources under `/api/projects/:projectId/{resource}` (`ceremonies`, `routing`, `mcp-servers`, `review-policies`, `ralph-monitor`). `squad-sync` is explicit about the Squad/Squadboard state surface and avoids overloading generic sync semantics already associated with GitHub sync operations.

Retired names such as generic sync or client-artifact-only resources must not appear in new API contracts.

## Source-of-Truth Modes

Every project has a **canonical storage mode** set at creation time and persisted in `projects.storage_provider_mode` (DB column).

### Mode: `fs` (Filesystem Authority)

- **Authoritative:** Real files under `.squad/`
- **Where it lives:** Project Git repository
- **SDK storage backend:** `FilesystemStorageProvider` (default for local CLI work)
- **Import semantics:** On first application load, if `squad_storage` table is empty, pre-populate it from `.squad/` (one-time only)
- **Projection/sync:** Squadboard reads `.squad/` for context but does not write back. External clients read `.squad/` directly (or via Squadboard API).
- **Best for:** CLI-first projects, local teams, full Git control

### Mode: `postgresql` (Database Authority)

- **Authoritative:** `squad_storage` table in Squadboard PostgreSQL (or PGlite for local dev)
- **Where it lives:** Squadboard database
- **SDK storage backend:** `PostgreSQLStorageProvider`
- **Import semantics:** On first write, if table is empty and `SQUAD_FS_BOOTSTRAP_PATH` is set, import from filesystem once, then DB owns state
- **Projection/sync:** Squadboard generates `.squad/`, `.github/agents/squad.agent.md`, and ceremonies defaults on read/apply. Filesystem becomes a read-only cache.
- **Best for:** Squadboard-first, multi-surface teams, hosted deployments

### Mode: `pglite` (Deprecated → PostgreSQL)

**No longer a distinct mode.** All local in-process database work uses `postgresql` with PGlite as the concrete DB backend. Stale decision inbox entries mentioning "pglite mode" should be archived.

## Bootstrap and Projection Artifacts

### `.squad/` Directory Structure

**Owner (by mode):**
- `fs` mode: Filesystem (authoritative)
- `postgresql` mode: Generated by Squadboard from `squad_storage` (read-only cache)

**Contents (canonical):**
```
.squad/
  ├─ team.md                        # Team roster, project context
  ├─ routing.md                     # Ceremony routing rules
  ├─ decisions.md                   # Team decisions + history (append-only)
  ├─ ceremonies.md                  # Ceremony triggers + workflows
  ├─ config.json                    # Project-level Squad config
  ├─ agents/                        # Hired agent charters, histories (per agent)
  │  └─ {agent-name}/
  │     ├─ charter.md
  │     └─ history.md
  ├─ decisions/inbox/               # Pending directives (append-only)
  ├─ casting/                       # Casting registry + history
  ├─ orchestration-log/             # Machine-readable workflow logs
  ├─ log/                           # Session/work logs
  ├─ reports/                       # Generated health/sync reports
  └─ skills/                        # Reusable skill templates
```

### `.github/agents/squad.agent.md`

**Owner:** Squadboard (generated artifact)  
**When created:**
- On first Squadboard API read of the project
- On project create/bootstrap from UI
- On explicit "repair/regenerate" action

**How it gets there:**
1. Squadboard reads canonical `.squad/team.md`, `routing.md`, `ceremonies.md` from DB (if `postgresql` mode) or filesystem (if `fs` mode)
2. Renders **squad.agent.md** from template + team context
3. Writes to `.github/agents/squad.agent.md` (via API or Git commit if authorized)
4. Copilot/CLI reads `.github/agents/squad.agent.md` → understands team, ceremonies, routing

**If missing (e.g., started in Squadboard, not yet pushed to Copilot):**
- Copilot/CLI enters "init mode" and proposes a fresh team
- User can later sync via API: `POST /api/projects/:projectId/squad-sync/generate-github-agent` → regenerates and pushes `.github/agents/squad.agent.md`

---

### Ceremonies Defaults

**Owner:** Squadboard  
**When seeded:**
- On project create (from `docs/templates/ceremonies-defaults.md`)
- On explicit "seed defaults" action

**Invariant:** `ceremonies.md` must not be absent, empty, or a placeholder-only default. A missing file, empty file, or default-missing content is a sync health warning and a required repair item (`seed-ceremony-defaults`), not a valid steady state.

**Contents (predefined templates):**
- Simple Review
- Bug Fix
- RFC
- Spike
- Pair Programming

**How users extend:**
- Edit `.squad/ceremonies.md` directly (if `fs` mode)
- Or use Squadboard UI → Squadboard writes to `squad_storage` → projects can re-project to `.squad/ceremonies.md` on sync

## Sync Semantics: Explicit Modes, Not Implicit Magic

### One-Way Projection (`fs` → Squadboard read)

**When:** Project in `fs` mode  
**Flow:**
1. Squadboard API reads `.squad/` on each request (or caches per-session)
2. Displays team, routing, decisions in UI without modifying them
3. UI is advisory; truth remains in Git

**Risk:** Stale decisions if `.squad/decisions.md` not updated

### One-Time Import (`fs` → PostgreSQL first-run)

**When:** Project in `postgresql` mode, first time `squad_storage` table is accessed  
**Flow:**
1. Check if `squad_storage` table has rows for this project scope
2. If empty AND `SQUAD_FS_BOOTSTRAP_PATH` env var points to valid `.squad/`, read all `.squad/` files
3. Insert rows into `squad_storage` with `(scope, path, content)` triples
4. Mark import complete in `squad_storage` metadata row (special key: `__bootstrap_source_fs`)
5. DB now owns state; filesystem becomes a cache

**Idempotency:** Marked by `__bootstrap_source_fs` key. Re-running import is a no-op; explicit "force-reimport" requires API call with `force: true`.

### Projection from DB to Filesystem (PostgreSQL mode only)

**API:** `POST /api/projects/:projectId/squad-sync/project-squad-to-fs`
**When called:**
1. Read all `squad_storage` rows for this project
2. Write to `.squad/`, overwriting existing files
3. Return diff (what changed)

**Idempotency:** Safe to call repeatedly; only writes if content differs.

**Error handling:** If write fails after partial success, return `{status: 'partial_failure', written: [...], failed: [...], repair_instructions: '...'}`.

### Generate Client Agent File

**API:** `POST /api/projects/:projectId/squad-sync/generate-github-agent`
**When called:**
1. Read team, routing, ceremonies from authoritative mode (DB or filesystem)
2. Render `.github/agents/squad.agent.md` from template
3. Write to repository (via Git API or blob push)
4. Return path and version

**Failure handling:** If not authorized to write to GitHub, return `{status: 'auth_required', guidance: 'Ask admin to configure GitHub token'}`.

**Endpoint:** `GET /api/projects/:projectId/squad-sync/status`
**Returns:**
```json

  "project_id": "proj-123",
  "storage_mode": "postgresql",
  "bootstrap_status": "completed",
  "bootstrap_source": "fs",
  "bootstrap_timestamp": "2026-05-19T12:00:00Z",
  "drift_status": "clean" | "warning" | "critical",
  "drifts": [
    {
      "surface": "github_agent_file",
      "status": "missing",
      "path": ".github/agents/squad.agent.md",
      "advice": "Call POST /api/projects/:projectId/squad-sync/generate-github-agent to regenerate"
    },
    {
      "surface": "filesystem_squad",
      "status": "diverged",
      "files": {".squad/ceremonies.md": "10 days stale"},

    }

  "last_sync_timestamp": "2026-05-19T13:00:00Z"

```

### Repair Commands

**UI:** Project settings → **Team Sync** panel lists each surface and "Repair" button per drift type.

**API:** `POST /api/projects/:projectId/squad-sync/repair`
```json
{
  "action": "regenerate_github_agent" | "sync_squad_to_fs" | "reimport_fs_to_db",
  "force": false
}
```

## Startup and Initialization Flows

### Squadboard-First (Web UI)

1. **User creates project in UI** → name, language, team size
2. **Squadboard:**
   - Creates `projects` row with `storage_provider_mode = 'postgresql'`
   - Calls `setup-lifecycle` to initialize `.squad/` structure in memory
   - Inserts into `squad_storage` (team.md, routing.md, ceremonies.md defaults, agents)
3. **User later opens in Copilot/CLI:**
   - Finds no `.github/agents/squad.agent.md`
   - Enters init mode → proposes team
   - User can: (a) confirm new team (overwrites), or (b) say "sync from Squadboard" → calls API → regenerates agent file

**Bootstrap gap:** None — ceremonies are pre-seeded in Squadboard.

### CLI/Copilot-First (Local Hacking)

1. **User starts with Copilot/CLI** → creates `.squad/` manually or via `copilot squad init`
2. **Copilot SDK:**
   - Detects no Squadboard DB
   - Sets `storage_provider_mode = 'fs'` (implicit; filesystem is the default)
   - Reads/writes `.squad/` directly
3. **User later creates Squadboard project** → links to same Git repo + `.squad/` path
4. **Squadboard:**
   - Detects existing `.squad/` directory
   - Offers: (a) import to DB (move to `postgresql` mode), or (b) stay in `fs` mode
   - If import: calls bootstrap one-time import, inserts `projects.storage_provider_mode = 'postgresql'`

## Squad SDK Responsibilities

**What the SDK owns:**
- `StorageProvider` abstraction (interface)
- `FilesystemStorageProvider` implementation
- `PostgreSQLStorageProvider` implementation
- Read/write APIs for `.squad/` artifacts (agnostic to backend)
- Bootstrap import logic (one-time, idempotent)

**What the SDK does NOT own:**
- Deciding which mode is authoritative (application layer decides)
- Generating client agent files (Squadboard service layer)
- Deciding when to sync (API layer via explicit endpoints)
- UI or CLI command routing (client layer)

**The pattern:** Application calls SDK like this:

```typescript
// In Squadboard backend
const provider = resolveStorageBackend(project.storage_provider_mode);

// Read
const teamMd = await provider.readContent(project.squadPath, 'team.md');

// Write (only if mode is 'fs' AND explicit permission, or if mode is 'postgresql' AND caller is Squadboard)
if (project.storage_provider_mode === 'postgresql' && caller.is_squadboard_api) {
  await provider.writeContent(project.squadPath, 'team.md', newContent);
}

// In Copilot/CLI
const provider = resolveStorageBackend('fs'); // hardcoded for CLI
const ceremoniesYaml = await provider.readContent(cwd + '/.squad', 'ceremonies.md');
```

## Multi-Surface Team Workflows

### Scenario 1: Squadboard-First, Then Copilot

1. Ahmed creates Squad project in Squadboard UI
2. Backend stores `storage_provider_mode = 'postgresql'`
3. Ahmed opens Copilot/CLI on the same repo
   - Copilot CLI reads `.github/agents/squad.agent.md` (either exists from previous Squadboard export, or doesn't)
   - If missing: Copilot enters init mode; Ahmed says "no, use board team" → API sync
   - If present: Copilot loads team from agent file → ceremonies ready
4. Ahmed runs Copilot agent
   - Agent makes decision → calls `captureDirective()` → writes `.squad/decisions/inbox/` AND calls MCP `capture` tool → Squadboard records it
   - Decision flows into board via webhook or MCP broker
5. Ahmed checks Squadboard UI
   - Sees the decision in inbox, approves it → writes to `.squad/decisions.md` via API
   - Next Copilot run sees updated decisions (reads `.squad/decisions.md` via `fs` projection or SDK read)

### Scenario 2: CLI-First, Then Squadboard

1. Ahmed starts with `copilot squad init` → builds `.squad/` on disk
2. Copilot CLI stores `storage_provider_mode = 'fs'` (default)
3. Ahmed makes decisions locally → written to `.squad/decisions.md`
4. Ahmed later creates Squadboard project, links to same repo
5. Squadboard offers import wizard:
   - "Stay in filesystem mode (Squadboard reads `.squad/` as advisory)" → `fs` stays
   - "Move to database mode (faster, sync across surfaces)" → calls bootstrap import, sets `postgresql`
6. If moved to `postgresql`:
   - Existing `.squad/` files imported to `squad_storage`
   - Squadboard generates `.github/agents/squad.agent.md` from DB state
   - Next Copilot CLI run sees updated agent file
7. Ahmed continues working:
   - Copilot CLI: Reads `.squad/` → if `fs` mode, reads real files; if `postgresql`, reads projected `.squad/` (refreshed via periodic sync API call)
   - Squadboard: Writes decisions/ceremonies/routing → syncs to `.squad/` via `POST /api/projects/:projectId/squad-sync/project-squad-to-fs`

### Scenario 3: Both Start Together

1. Ahmed sets up Squadboard project + Copilot repo in parallel
2. Chooses: Single database (`postgresql` mode) for shared state
3. On first Squadboard run: Exports `.github/agents/squad.agent.md` to Git
4. On first Copilot run: Reads agent file → understands team
5. Both read/write to same `squad_storage` via Squadboard API or local PostgreSQL connection
6. All work converges in one place; no divergence because one source of truth

## Migration Path (Existing Projects)

For projects already created (before this work):

1. **Retroactive mode assignment:** Default existing projects to `fs` mode (filesystem authority) — safest default
2. **Offer import:** In Squadboard UI, show "Upgrade to multi-surface mode" option → calls bootstrap import, switches to `postgresql`
3. **No forced migration:** Users choose when to move to database mode; CLI projects stay `fs` until explicitly switched

## Open Questions (Deferred)

- **Q1:** Should `storage_provider_mode` be user-configurable, or is it one decision per project lifetime?
  - **Answer:** One per lifetime for now. Rare case to switch modes; add explicit "migrate mode" API if needed later.
- **Q2:** If filesystem `.squad/` is stale compared to DB `squad_storage`, which wins?
  - **Answer:** Depends on mode. In `fs` mode, filesystem wins (it's truth). In `postgresql` mode, DB wins; filesystem is a cache. Sync API makes it explicit which direction data flows.
- **Q3:** Can ceremonies be edited in both Squadboard UI and `.squad/ceremonies.md` simultaneously?
  - **Answer:** No — they are one artifact. In `fs` mode, edit the file directly. In `postgresql` mode, edit in UI (or edit file + call sync API to import changes back to DB). Simultaneous edits cause last-write-wins (non-deterministic).

## Summary

**The contract:**
1. Every project has one storage mode: filesystem (`fs`) or database (`postgresql`).
2. That mode determines where `.squad/` is authoritative.
3. Squadboard generates/projects client artifacts (agent file, ceremonies defaults).
4. Sync is explicit — specific API calls with clear input/output, not continuous mirroring.
5. Drift is detected and reported; repair is user-initiated.

**The seams:**
- Bootstrap import: `fs` → PostgreSQL (one-time, idempotent)
- Projection: PostgreSQL → `.squad/` (one-way, repeatable)
- Generate client artifacts: Authoritative mode → `.github/agents/squad.agent.md`
- Capture directive: `.squad/decisions/inbox/` + DB inbox + MCP capture (unified intake)

**For users:**
- Start anywhere (Squadboard web, CLI, Copilot) — Squadboard lets you link later
- Sync is available but not forced
- Ceremonies are pre-seeded; no empty stubs
- Team state stays in sync because one source of truth is always authoritative
